# Лабораторна робота №5

## Тема та мета: Налаштування системи моніторингу для відстеження стану сервера та продуктивності вебзастосунку.

Мета роботи — розгорнути та налаштувати стек моніторингу Prometheus + Grafana для:

- збору системних метрик віртуальної машини (CPU, RAM, диск, мережа),
- збору метрик контейнерів Docker,
- збору прикладних метрик Flask-застосунку,
- візуалізації та аналізу показників (пошук аномалій, піків навантаження).

## Теоретичні відомості: Коротко про Prometheus (TSDB), Grafana (візуалізація), Node Exporter (метрики заліза) та cAdvisor (метрики контейнерів). Поясни концепцію "Scraping" метрик.

**Prometheus** — система моніторингу та алертингу, що працює за pull-моделлю: регулярно опитує (scrape) HTTP-ендпоінти експортерів/застосунків і зберігає отримані значення у вбудованій часовій базі даних **TSDB** (time-series database). Дані зберігаються як часові ряди: `metric_name{labels} value @timestamp`.

**Grafana** — платформа візуалізації, яка підключається до джерел даних (зокрема Prometheus) і будує дашборди: графіки, таблиці, алерти, панелі зі статусами.

**Node Exporter** — експортер системних метрик ОС/вузла ("заліза"): завантаження CPU, використання RAM, файлових систем, мережі, load average тощо. Для контейнеризованого розгортання Node Exporter монтує `/proc`, `/sys` та корінь FS у read-only режимі.

**cAdvisor** — експортер метрик контейнерів (Docker): CPU/RAM/IO/мережа по контейнерах, а також агреговані показники. Корисний для аналізу впливу кожного сервісу на ресурси хоста.

**Scraping (збір метрик)** — процес періодичного HTTP-запиту Prometheus до цільових ендпоінтів, які віддають метрики у Prometheus-форматі (звичайно це `http://target/metrics`). У даному проєкті прикладні метрики Flask віддаються окремим HTTP-сервером на порту `8001` (ендпоінт `/metrics`), а експортери доступні за внутрішніми DNS-іменами Docker-мережі.

## Опис інфраструктури:

### Cloud: Oracle Cloud Infrastructure (OCI).

Використано хмарну платформу **Oracle Cloud Infrastructure (OCI)** для розгортання віртуальної машини та публічного доступу до вебзастосунку і Grafana.

### OS: Oracle Linux 9.

ОС інстанса: **Oracle Linux 9**, що підтримує `firewalld`/`firewall-cmd`, Docker та системні утиліти адміністрування.

### Instance: VM.Standard.E2.1.Micro (зазначити проблему обмеження RAM у 1 ГБ та використання Swap на 3 ГБ).

Тип інстанса: **VM.Standard.E2.1.Micro** з обмеженням **RAM ≈ 1 ГБ**. Через одночасний запуск кількох сервісів (Flask, Prometheus, Grafana, Node Exporter, cAdvisor) можливі піки споживання памʼяті.

Практичне рішення — увімкнути **Swap ~ 3 ГБ** для стабілізації системи під навантаженням. Swap знижує ризик OOM-killer, але може погіршити latency при інтенсивному свопінгу, тому:

- обмежено памʼять контейнерів (ліміти у `docker-compose.yml`),
- відкрито назовні лише необхідні порти (Grafana та метрики застосунку).

### Мережеві налаштування (Таблиця портів):

|        Порт | Компонент                               | Призначення                      | Доступність                                          |
| ----------: | --------------------------------------- | -------------------------------- | ---------------------------------------------------- |
|        8000 | Вебзастосунок (Flask)                   | UI/сторінка дашборду             | Публічно                                |
|        8001 | Ендпоінт метрик застосунку (`/metrics`) | Прикладні метрики для Prometheus | Публічно для перевірок + внутрішньо для Prometheus |
|        3000 | Grafana Dashboard                       | Візуалізація                     | Публічно                                             |
|        9090 | Prometheus                              | UI/API Prometheus                | Внутрішньо                   |
| 9100 / 8080 | Експортери                              | Node Exporter / cAdvisor         | Внутрішньо                   |

Примітка: у `docker-compose.yml` порти Prometheus/експортерів можуть бути проброшені на хост для локальної діагностики, але на рівні **OCI Security List** та **firewalld** вони мають залишатися недоступними з Інтернету.

### Конфігурація безпеки (OCI Security List & Firewall-cmd): Опиши процес відкриття портів 3000 та 8001 для доступу ззовні.

Процес відкриття портів складається з двох рівнів: **хмарні правила** (OCI) та **локальний фаєрвол** (Oracle Linux 9).

1. **OCI (VCN Security List / Network Security Group)**

- Додано Ingress-правила для TCP-портів `3000` (Grafana) та `8001` (метрики застосунку).
- Для підвищення безпеки бажано обмежити `Source CIDR` (наприклад, лише власна IP-адреса), якщо немає потреби у публічному доступі для всіх.

2. **Oracle Linux 9 (`firewalld`)**

На інстансі відкрито лише необхідні порти:

```bash
sudo firewall-cmd --permanent --add-port=3000/tcp
sudo firewall-cmd --permanent --add-port=8001/tcp
sudo firewall-cmd --reload
sudo firewall-cmd --list-ports
```

При цьому порти `9090`, `9100`, `8080` не відкривалися назовні.

## Реалізація моніторингу: Опиши структуру docker-compose.yml, де об'єднані всі сервіси в одну мережу. Згадай налаштування prometheus.yml для збору даних з analytics-web:8001.

Моніторинг реалізовано через Docker Compose, де всі сервіси запускаються в одному стеку та автоматично потрапляють у спільну Docker-мережу, що дає:

- сервіс-дискавері за DNS-іменами контейнерів (наприклад, `analytics-web`, `node-exporter`, `cadvisor`),
- ізоляцію від зовнішнього світу за замовчуванням,
- керований і відтворюваний деплой.

**Склад сервісів у `docker-compose.yml`:**

- `web` — Flask-застосунок, що публікує порт `8000` (веб) і `8001` (метрики),
- `prometheus` — збір та зберігання метрик (TSDB), volume `prometheus_data`,
- `grafana` — візуалізація та дашборди, volume `grafana_data`,
- `node-exporter` — метрики хоста,
- `cadvisor` — метрики контейнерів.

Окремо в `web/app.py` використано бібліотеку `prometheus_client`: метрики віддаються на порту `8001`, стандартний шлях — `/metrics`.

**Налаштування Prometheus (`monitoring/prometheus/prometheus.yml`):**

- визначено `scrape_interval: 15s`,
- описано `scrape_configs` для Prometheus, Node Exporter, cAdvisor та Flask-сервісу,
- для застосунку задано target `analytics-web:8001`, що працює завдяки внутрішньому DNS Docker-мережі:

```yaml
- job_name: "analytics-web"
  static_configs:
    - targets: ["analytics-web:8001"]
```

## Демонстрація роботи: Опиши процес тестування навантаження за допомогою Bash-скрипту з нескінченним циклом (while true; do curl...).

Для демонстрації приросту прикладних метрик (лічильник HTTP-запитів) виконано генерацію навантаження простим Bash-циклом.

Приклад (на клієнті або на самому сервері):

```bash
#!/usr/bin/env bash
set -euo pipefail

TARGET="http://<PUBLIC_IP>:8000/"

while true; do
  curl -s -o /dev/null "$TARGET"
  sleep 0.2
done
```

Після запуску скрипту:

- у Prometheus перевіряється доступність target `analytics-web:8001` (розділ `Targets`),
- у запитах PromQL відслідковується зростання лічильника `http_requests_total`,
- у Grafana будується графік (наприклад, `rate(http_requests_total[1m])`) для виявлення піків трафіку.

## Висновки: Чого навчилися, як моніторинг допомагає виявляти аномалії (наприклад, сплески трафіку).

У ході роботи:

- розгорнуто повний стек моніторингу Prometheus + Grafana у Docker Compose;
- налаштовано збір метрик з хоста (Node Exporter), контейнерів (cAdvisor) та прикладних метрик Flask;
- відпрацьовано практику безпечного відкриття портів у OCI та `firewalld` (публічні лише `3000` і `8001`);
- враховано ресурсні обмеження мікроінстанса (1 ГБ RAM) та використано Swap (~3 ГБ) для стабільності.

Моніторинг дозволяє швидко виявляти аномалії: наприклад, **сплески трафіку** видно за зростанням `rate(http_requests_total[...])`, а паралельні графіки CPU/RAM/IO допомагають відрізнити реальне навантаження від проблеми витоку памʼяті чи деградації дискової підсистеми.
